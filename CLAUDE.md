## Project overview

"Taku Monky" is an admin panel for a taquería (taco restaurant), built with **Flet** (Python wrapping Flutter). It is one piece of a larger, two-part system:

- **This repo (Python/Flet)**: a desktop admin app for the business owner — manage the menu, view stats, generate content, use an AI agent, etc.
- **Public-facing site (separate, static HTML)**: customer-facing menu page and a table/seating system (`mesas.html`), deployed to Hostinger. It is *not* built from this Python code. As of Phase 4, `index.html`, `menu-platillos.html`, `menu-bebidas.html`, `menu-postres.html`, `style.css`, and `catalogo.js` (all at the repo root, so the owner can FTP the whole folder as-is) are the real public menu site — wired to live data and verified, but **the owner is still polishing its visual finish himself, so it's not a finished deliverable**; see the dedicated section under Design rules below before touching it. `mesas.html` and `mesas.css` are still empty placeholders, for the not-yet-started table/seating system (Phase 5).

**The phased build plan lives in `Hey Claude Code, read this file..txt` at the repo root — read it at the start of a session to know what's done and what's next.** (The owner clears context often; that file is the running roadmap, this file is the stable reference.)

Both halves are meant to share the same data by reading/writing the same **Supabase** project (Postgres + REST API). Menu images are stored in **Cloudflare R2** (not Supabase Storage). Supabase Auth (login + persisted session, see `models/` below and `views/sesion_view.py`) is wired up as of Phase 2.0. `menu_view.py` reads real rows from `public.platillos` via `models/platillo_dao.py` as of Phase 2.1-2.5 (loading/empty/error states, async fetch), and as of Phase 2.6 the panel can create/edit/delete/hide platillos too — see `models/`/Architecture below. As of Phase 4, the public menu site reads `public.platillos` directly from the browser with the anon key (`persistSession: false`, same pattern as `EJEMPLOS/supabase-config.js`), completely independent of the Flet panel — no Python code is involved in serving it, and the panel has no way to reach a customer's browser (see the dedicated Phase 4 section below for why that matters for cache freshness). ## Design rules (non-negotiable)

This project's visual identity is already established. **Never redesign, re-theme, or "modernize" existing screens while adding functionality.** When wiring up data, change only the data source — the layout, spacing, typography, and colors stay exactly as they are.

When you build something *new* (a dialog, a form, an empty state, an error toast), it must look like it was always part of the app — reuse the same palette, radii, and text styles from the surrounding view:

- **Palette** (hardcoded hex inline on controls; no theme file — keep it that way):
  - `#fbf5e9` page background · `#f8f1de` card/row surface · `#eee5cf` table header · `#eadfca` borders
  - `#0d0905` sidebar / primary button · `#1c1610` and `#18120d` primary text
  - `#f4ca83` gold accent · `#ffa200` and `#e8aa3a` warm accent · `#bf571d` / `#c86a28` orange highlight
  - `#5e5449`, `#7c7267`, `#8a7e72`, `#806f61` muted text · `#b58a6d` section eyebrow labels
  - Status: `#7d8545` green (visible/ok) · `#d9534f` red (destructive)
- **Typography**: display headings use `font_family="Georgia", italic=True` (sizes ~40–48 for page titles, ~15–19 inline). Small uppercase eyebrow labels are `size=11-13, weight="bold"` in `#b58a6d`/`#806f61`. Body text is default font, `size=12-15`.
- **Shapes**: pill buttons `border_radius=30`, cards `border_radius=14-16`, badges `border_radius=12`, icon buttons 30×30 with `border_radius=15` and `ink=True`.
- **Spacing**: views pad `left=36, right=36, top=42, bottom=36`; vertical gaps use `ft.Container(height=N)` spacers rather than margins.

If a design decision isn't already answered by an existing view, ask rather than inventing a new style.

### `views/components/dialogo_platillo.py` (Phase 2.6 — the add/edit form)

`DialogoPlatillo(router, on_guardado, platillo=None)` is a class, not a view — it builds and owns an `ft.AlertDialog` and is opened via `.abrir()` from `menu_view.py`'s "Agregar platillo" button and pencil icons. `platillo=None` → create mode; `platillo=<dict>` → edit mode, prefilled, with an extra red "Eliminar platillo" button (opens a second stacked confirm dialog before actually deleting — Flet supports stacking `show_dialog()` calls). Follows the same card language as `sesion_view.py` (420-wide card, same field styling, same `tight=True` Column gotcha) and the same red error-box styling used there and in `menu_view.py`.

Two things worth knowing if you touch this file:
- **The dialog has an explicit `X` close button (`boton_cerrar`, top-right, positioned via `ft.Stack`).** `AlertDialog(modal=True)` blocks both barrier-tap-to-dismiss and Escape in this Flet version — without an explicit close control there is *no* way to cancel the form once opened. Don't remove it or drop `modal=True` as "simpler"; both are needed together.
- **`_ocupado`/`_set_cargando()` guards `_cerrar()`** so the X can't cut off an in-flight save/delete. Because of that guard, every success path (`_guardar`, `_eliminar_async`) must call `self._set_cargando(False)` *before* `self._cerrar()`, not after — this was a real bug caught during Fase 2.6 verification (the guard was added first, and the success paths silently forgot to clear it, which would have made a successful save appear to hang since `_cerrar()` refused to close). If you add another exit path, keep that ordering.

**Phase 3 additions** (photo picker): a `fila_foto` row (72×72 preview + "Agregar/Cambiar foto" pill button + caption) sits right below the title, above `campo_nombre` — reuses the neutral input-surface colors (`#eadfca` border / `#f8f1de` bg) already established by the text fields, just applied to a button. The preview falls back to `assets/taco.jpg` via `error_content` exactly like `menu_view.py`'s table thumbnails. File selection is **Tkinter** (`_elegir_archivo_imagen()`, module-level function, a hidden `tk.Tk()` root + `filedialog.askopenfilename()`), not Flet's `FilePicker` — an explicit owner preference ("nunca he logrado hechar a andar el filepicker de flet"), not a limitation of this Flet version; always called via `asyncio.to_thread`, since it's a real blocking native dialog. `_set_cargando()` gained a `texto` param so `boton_guardar` can show which step is running (`"Optimizando imagen..."` → `"Subiendo foto..."` → `"Guardando..."`) instead of a bare spinner, since a save can now involve two slow steps before Supabase is even touched. `on_guardado` now takes one optional argument — see the `models/cloudflare_storage.py` section below for what it carries and why.

### `models/cloudflare_storage.py` (Phase 3 — Cloudflare R2 uploads/deletes)

Cloudflare's counterpart to `platillo_dao.py`, and deliberately a **separate file** — this one has nothing to do with Supabase. `validar_y_comprimir()` (Pillow: validates the file is a real image and under 15 MB, corrects EXIF rotation, downsizes to a 1600px longer side, re-encodes WebP quality 80 — same numbers as `EJEMPLOS/lilshop.html`'s `<canvas>` version) and `subir_imagen()`/`eliminar_imagen()` (`httpx`, POST/DELETE to the `taku-monky-uploads` Worker with the admin's Supabase session `access_token` in `Authorization`, same auth pattern as `EJEMPLOS/index.js`) are all **synchronous/blocking**, same convention as `PlatilloDAO` — `dialogo_platillo.py` is the one that wraps each call in `asyncio.to_thread`.

**Reverse-rollback order** (explicit owner requirement, mirrors `EJEMPLOS/lilshop.html`): alta uploads the photo *before* inserting the row, and deletes it if the insert then fails; editing uploads the new photo, updates the row, and only deletes the *old* photo *after* that update succeeds; deleting a platillo deletes the row first (via `PlatilloDAO.eliminar()`) and only then its photo. All three orderings live in `dialogo_platillo.py`'s `_guardar()`/`_eliminar_async()`, not in this module — this file only exposes the pieces.

**Orphan handling — this was the owner's #1 concern for this phase**, from a bad experience on Anxie Store where `EJEMPLOS/lilshop.html`'s `borrarImagenDeR2()` swallows any R2 delete failure into `console.error` and moves on, silently, forever. This project does the opposite by design, decided without re-asking (the owner explicitly delegated the "how"): `eliminar_imagen()` never swallows a failure — it (1) logs the technical detail to console, (2) **appends** a record (filename, full URL, reason, timestamp) to `%LOCALAPPDATA%\TakuMonky\huerfanos_r2.json` (same folder as `sesion.json`, outside the repo, never truncated so older undealt-with orphans aren't lost), and only then (3) raises `LimpiezaImagenFallida`. The caller in `dialogo_platillo.py` reacts differently depending on *when* the failure happens: a rollback-after-a-failed-save just swallows it (nothing was persisted, the orphan log is enough); a cleanup *after* a successful save/delete surfaces a message through `on_guardado(aviso_limpieza)`, which `menu_view.py._on_guardado()` shows via the existing red banner (`_mostrar_error_temporal` — reused as-is, there's no separate "warning" visual language in this project, so the copy itself makes clear the main action already succeeded). If you add a third call site that deletes an R2 image, give it the same two-tier treatment.

`TAMANO_MAXIMO_ORIGINAL` (15 MB) is deliberately generous — it exists to reject genuinely broken input, not ordinary phone photos (the owner's own example was 4 MB originals, which must be accepted and then compressed, never rejected).

### `models/platillo_dao.py` write methods — the RLS silent-failure gotcha

`crear`/`actualizar`/`eliminar`/`cambiar_visibilidad` were added in Phase 2.6. **All three of `actualizar`/`eliminar`/`cambiar_visibilidad` explicitly check that Supabase returned a non-empty `data` and raise `EscrituraSinEfecto` if not — this is load-bearing, not defensive fluff.** Unlike `INSERT`, a Postgres `UPDATE`/`DELETE` blocked by RLS doesn't raise an error: it just matches zero rows and returns HTTP 200 with `data: []`. This was caught live during Fase 2.6 verification — with a session that had no write grant, `cambiar_visibilidad()` returned success and the UI flipped a row's badge to "OCULTO" while the row was still `visible=true` in the real database. If you add another write method here, it needs the same `if not respuesta.data: raise EscrituraSinEfecto(...)` check, or a caller can end up trusting a write that never happened.

New platillos always get `orden = PlatilloDAO._siguiente_orden()` (max existing `orden` + 1) so they land at the *end* of the list — `orden` defaults to 0 in the table, so an insert that omits it would jump to the top.

**Phase 3**: `crear()`/`actualizar()` now also accept an optional `image_url` key in `datos` — included in the row sent to Supabase only when the key is present (so a save with no new photo never touches the column), never required. The actual upload/delete against Cloudflare happens in `models/cloudflare_storage.py`, called from `dialogo_platillo.py` *before* these DAO methods run — this file stays Supabase-only.

**Delete is physically real, and that was audited (2026-08-25)** — the owner asked, having been burned by a previous project. Verified with direct SQL through the Management API (which bypasses PostgREST entirely, so it can't be fooled by an API-layer illusion): the table has **no soft-delete column**, **no DELETE trigger**, and **no rewrite RULE** — `platillos_admin_delete` is a plain RLS policy, and `eliminar()` issues a real `DELETE`. `pg_stat_user_tables` showed `n_tup_del = 5` with gaps in the `id` sequence, i.e. rows the owner deleted from the panel are genuinely gone from Postgres. Edits are equally real: rows the owner edited show `updated_at > created_at`. There is also **no caching anywhere in the panel** — every view refetches on navigation. The one cache is `sessionStorage` in the *public* HTML (Phase 4, `catalogo.js`) — see the dedicated Phase 4 section below for how its freshness is actually kept up to date. It is **not** invalidated by the panel: an earlier draft of this file said it would be, but that's not physically possible — this is a desktop app with no way to reach into a customer's browser, and even Anxie Store's browser-side invalidation only ever cleared the *owner's own* browser, never a customer's. Freshness comes entirely from a short client-side TTL plus active refresh, not from any signal sent by this panel. Dead tuples (38 at audit time, table 64 kB) are ordinary Postgres MVCC and get reclaimed by autovacuum — not a leak, and not worth acting on at this size.

If you do rework the CSS/markup on request, keep the contract `catalogo.js` depends on intact: the ids `#contenedor-platillos` / `#contenedor-bebidas` / `#contenedor-postres` / `#contenedor-grid` / `#subtitulo-categoria` / `#enlace-whatsapp-hero` / `#enlace-whatsapp-footer`, the section ids `#platillos` / `#bebidas` / `#postres` (the navbar anchors and the hide-empty-category logic both use them), and the `.tk-tarjeta` / `.tk-spinner` classes the JS generates and queries.

The public-facing site is plain HTML/CSS/JS, no build step, no npm, meant to be FTP'd to Hostinger as-is — all 6 files live flat at the repo root (not a subfolder) for exactly that reason. It reads `public.platillos` directly from the browser with the anon key; the Flet panel plays no part in serving it and can't reach it at runtime.

**`catalogo.js`** is the *only* JS file, shared by all 4 HTML pages — deliberately, so the card markup and the Supabase/cache logic exist in one place, not copy-pasted four times. It folds together what `EJEMPLOS/supabase-config.js` and `EJEMPLOS/catalog-cache.js` do separately:
- Supabase client: same `persistSession/autoRefreshToken/detectSessionInUrl: false` as the EJEMPLOS pattern. Keep this even if it looks unnecessary later — it's what prevents the Anxie Store failure mode (browser tracking-prevention blocking `localStorage` → the SDK repeatedly reinitializing auth → ~312 redundant `pg_timezone_names` queries, 67% of DB time), not a caching decision.
- `obtenerCatalogo({ forzar })` — one query for the *entire* visible catalog (`select` limited to the columns the cards render, `.eq("visible", true)` explicit alongside RLS, ordered by `orden` then `id`), cached in `sessionStorage` under `taku_monky_catalogo_v1`. The index page fans this single list out into its 3 preview sections client-side rather than querying per category, and a category page navigated to from the index reuses the same still-warm cache instead of re-querying.
- `tarjetaPlatilloHTML(platillo)` — the one card template, used by both the index previews and the full category grids. If the card design changes, it changes here only.
- `agruparPorCategoria()` / `htmlEstadoCargando()` / `htmlEstadoError()` / `htmlEstadoVacio()` — shared grouping and state rendering, matching `menu_view.py`'s loading/empty/error visual language (gold spinner, red error box, icon+text empty state) adapted to CSS/inline SVG.

**Cache TTL is 30s, not the 5 minutes originally sketched in the roadmap** — and the roadmap's old claim that "the Flet panel invalidates this cache after every write" was wrong and has been corrected there, not carried forward: a desktop app has no mechanism to reach into a customer's browser (not even Anxie Store's version did that for anyone but the owner). Freshness instead comes from two things working together, both in `catalogo.js`:
1. A short TTL. Safe to keep short because the original Anxie Store incident was never actually about query *frequency* — it was the `persistSession` failure mode above, which is already closed off. A 7-row table costs nothing to query every 30s per visitor.
2. `iniciarAutoRefresco()` — refetches when the tab regains visibility, and every `CACHE_DURACION_MS` while it stays visible, so a page left open (e.g. at a table) self-corrects without a manual reload.

**A real bug was found and fixed here during Phase 4 verification, worth knowing if you touch the cache logic**: the refresh interval fired every 30000ms — the same number as the cache TTL. A tick landing a few milliseconds after the *previous* tick's fetch had refreshed the cache would see it as "still fresh" by that margin and skip the fetch, silently doubling the worst-case staleness to ~60s on roughly half of all ticks. Live-tested proof: hiding a platillo showed up in an already-open tab in 27.2s (fine), but un-hiding it took over 40s (the bug). Fix: `obtenerCatalogo()` takes a `{ forzar: true }` option that bypasses the cache read entirely, and `iniciarAutoRefresco()` always passes it on both the interval and the visibility-change trigger — only a page's *initial* load respects the cache. Re-tested after the fix: 27.2s / 28.2s / 26.2s / 25.2s across four separate live mutations, all within the intended bound. If you ever change `CACHE_DURACION_MS` or the interval period independently of each other, re-check this — the bug only exists when the two numbers match exactly.

**WhatsApp number is a placeholder on purpose** (`5215500000000` in `NUMERO_WHATSAPP`, top of `catalogo.js`, one constant feeding both the hero and footer buttons on all 4 pages) — the owner explicitly asked for an obviously-fake number, not a real or invented one. Don't reuse `sidebar.py`'s WhatsApp number for this — that one is the owner's personal support contact with the developer ("Te respondemos en WhatsApp"), not the business's public order line.

**Card image**: `image_url` or `assets/taco.jpg` if `NULL` — same fallback the panel's table already uses, reused rather than inventing a second placeholder. Falls back the same way via `onerror` if a real R2 URL fails to load. As of Phase 4 essentially every platillo has no photo yet, so this is the *normal* rendering, not an edge case — verified visually, not just assumed.

**Empty category handling differs by page on purpose**: on the index, a category with zero visible platillos hides its whole preview section (`display:none`) rather than showing a half-empty box. On that category's own full page, the section can't hide (it's the entire page), so it shows the same empty-state language as the panel's `_estado_vacio()` instead. `Postres` had zero visible rows at the time this was built and verified, so both branches were exercised for real, not just in theory.

**Don't reuse `assets/img1.jpg`–`img4.jpg` for anything menu-related** — opened during Phase 4 verification, they turned out to be promotional artwork for an unrelated business ("Sushi Joy"), already used only as mockup thumbnails in `contenido_view.py` (Phase 7 placeholder screen). Not Taku Monky's own photography.

**Domain**: none yet at the time of Phase 4 — all 4 pages link to each other with relative paths (`menu-bebidas.html`, never absolute), so this doesn't block anything. Supabase's REST/Auth API is CORS-permissive by default regardless of origin (the anon key + RLS is the security boundary, not an origin allowlist), so no CORS configuration is pending on a domain either.

## Running the app

```bash
python main.py
```

This launches the Flet desktop app (`ft.run(main, assets_dir=".")` in `main.py`), which opens a maximized native window titled "Taku Monky - Panel" — showing `SesionView` (login) if there's no valid saved session, or the usual Sidebar+panel if there is. See `models/sesion.py`.

There is no build step, linter, formatter, or test suite configured in this repo (no `pyproject.toml`, no test files). Dependencies are pinned in `requirements.txt` (`flet`, `supabase`, `python-dotenv`, `httpx`, `pillow`) and installed in the active Python environment — install with `pip install -r requirements.txt` if a fresh environment is missing any of them (`supabase`/`python-dotenv` in particular aren't part of a bare Python install).

**Public site** (`index.html` and the 3 `menu-*.html` pages) has no build step either — it's meant to be uploaded to Hostinger as-is. To preview it locally, serve the repo root as static files (e.g. `python -m http.server 8123`) and open `http://localhost:8123/index.html`; opening the file directly via `file://` can behave differently for `sessionStorage`/`fetch`, so prefer a real (even if local) HTTP origin when testing.

## Architecture

**MVC-ish structure, single window, no real routing:**

- `main.py` — entry point; creates the Flet `Page` and hands it to `MainController`.
- `controllers/main_controller.py` — `MainController` acts as the app's router/state holder (referred to as `router` throughout the view/component code). It owns:
  - `self.vista_actual` — name of the currently active view (`"home"`, `"menu"`, `"agente_financiero"`, `"contenido"`, `"ajustes"`, `"biblioteca"`).
  - `self.view_switcher` — an `ft.AnimatedSwitcher` that swaps view content with a scale transition.
  - `cambiar_vista(vista: str, abrir_dialogo_nuevo: bool = False)` — the *only* navigation mechanism: instantiates the matching view class, sets it as the switcher's content, and rebuilds the `Sidebar` so its active-button highlighting stays in sync. There is no separate router/state-management library. `abrir_dialogo_nuevo` (added Phase 2.7) is a one-shot, non-persisted flag forwarded straight into `MenuView`'s constructor when `vista == "menu"` — it exists only so `home_view.py`'s "Agregar un producto nuevo" shortcut can land on Menú with the add dialog already open. Every other caller (the sidebar, the other atajo, every `cambiar_vista("contenido")` call) omits it and gets the unchanged default behavior — there's no router-level state that could leak into a later, unrelated navigation.
- `views/*.py` — one file per screen (`home_view.py`, `menu_view.py`, `agenteIA_view.py`, `contenido_view.py`, `ajustes_view.py`, `biblioteca_view.py`). Every view follows the same shape:
  ```python
  class SomeView(ft.Container):
      def __init__(self, router):
          super().__init__()
          self.router = router
          self.expand = True
          self.height = float("inf")
          self.bgcolor = "#fbf5e9"
          self.content = ft.Column(...)  # built inline in __init__
  ```
  Views are rebuilt from scratch on every navigation (no persistent state between visits) and call back into the app only through `self.router` (e.g. `self.router.cambiar_vista(...)`, `self.router.page`).
- `views/components/sidebar.py` — `Sidebar(router)` is the persistent left nav (also takes `router` and reads `router.vista_actual` to highlight the active item). Includes a hardcoded WhatsApp support link.
- `views/components/dialogo_platillo.py` — `DialogoPlatillo`, the add/edit form dialog used by `menu_view.py` (Phase 2.6; gained the photo picker in Phase 3). See the dedicated sections under Design rules above — it's not just a form, it has several non-obvious gotchas (the explicit close button, the `_ocupado` ordering, the Tkinter file picker, the upload/rollback order) worth reading before touching it.
- `models/` — the data layer:
  - `supabase_client.py` — the one shared `Client`, created with `SUPABASE_ANON_KEY` via `create_client()`. Write access comes from whatever session is active on `client.auth`, not from the key. Also exposes `SUPABASE_ADMIN_EMAIL` (read from `.env`) so `SesionView` can prefill the email field.
  - `sesion.py` — `guardar`/`cargar`/`borrar`/`restaurar` persist the session (access_token, refresh_token, expires_at only — never the password) to `%LOCALAPPDATA%\TakuMonky\sesion.json`, outside the repo. `restaurar(client)` calls `client.auth.set_session(...)`, which refreshes the token itself if it expired; a failure there clears the saved file and returns `False`.
  - `platillo_dao.py` — `PlatilloDAO`, a DAO class following the `VentaDAO` pattern from `EJEMPLOS/ia_controller.py`. `obtener_todos()` (Phase 2.1-2.5): a blocking `client.from_("platillos").select(...)` call, `select()`-ing only the columns `menu_view.py` paints (`id, nombre, descripcion, categoria, precio, visible, image_url` — never `select('*')`, same rule as `EJEMPLOS/catalog-cache.js`), ordered by `orden` then `id`. `crear`/`actualizar`/`eliminar`/`cambiar_visibilidad` (Phase 2.6) round out the CRUD — see the dedicated "RLS silent-failure gotcha" note under Design rules above before touching any of them; `crear`/`actualizar` gained an optional `image_url` in Phase 3. `obtener_estadisticas()` and `obtener_recientes()` (Phase 2.7) back `home_view.py`'s two dynamic cards — the former makes 4 `count="exact", head=True` requests (1 total + 1 per fixed category), all filtered to `visible = true`, and never downloads row data; the latter selects `id, nombre, created_at, updated_at` ordered by `updated_at desc` and leaves the Nuevo/Editado interpretation to the view, not the DAO. None of the methods in this file catch exceptions themselves; failures are left to rise to the caller (`menu_view.py`/`dialogo_platillo.py`/`home_view.py`, via `asyncio.to_thread`), same division of labor as `sign_in_with_password` in `sesion_view.py`.
  - `cloudflare_storage.py` (Phase 3) — compresses (Pillow → WebP) and uploads/deletes platillo photos against Cloudflare R2 through the `taku-monky-uploads` Worker (`httpx`). See the dedicated section under Design rules above — in particular the orphan-logging behavior (`huerfanos_r2.json`) and the reverse-rollback order, both explicit owner requirements for this phase.
- `assets/` — images referenced by views/sidebar (e.g. `logomonky.png`) via relative `assets/...` paths, since `assets_dir="."` in `main.py`.
- `cloudflare/index.js` (Phase 3) — source of the deployed `taku-monky-uploads` Worker (see `models/cloudflare_storage.py` above). Reference/redeploy-only: nothing in the Python app imports it, it runs on Cloudflare's edge, not in this process.
- `index.html`, `menu-platillos.html`, `menu-bebidas.html`, `menu-postres.html`, `style.css`, `catalogo.js` (Phase 4) — the public menu site, entirely separate from everything above: no Python code runs it, no `main.py`/`MainController` involvement, nothing here imports from `models/`/`views/`. See the dedicated Phase 4 section under Design rules above for how it's structured and why the cache works the way it does.

**Adding a new screen** means: create `views/new_view.py` following the pattern above, import it in `main_controller.py`, add an `elif` branch in `cambiar_vista`, and add a nav button in `sidebar.py` via `self._crear_boton_menu(...)`.

**Exception — the login screen** (`views/sesion_view.py`, built in Phase 2.0): it is a *startup* screen, not a section of the panel, so it does **not** go through `cambiar_vista` and gets no sidebar button. `MainController.__init__` calls `models/sesion.py`'s `restaurar()` and decides between `mostrar_login()` (page holds only `SesionView`, full window, no `Sidebar`) and `mostrar_panel()` (builds `Sidebar` + content `Row` — this assembly now lives inside `mostrar_panel()` itself, not `__init__`, so it never exists unless there's a session). This means the app skips straight to the panel on relaunch as long as the saved session is still valid — that's intentional (see the roadmap's "Sesión viva"), not a bug; forcing a fresh login every launch would need an explicit product decision to change it. `cerrar_sesion()` (clears the saved session + signs out + calls `mostrar_login()`) exists on the router already but has no caller yet — it's meant to be wired to a button in `ajustes_view.py` (Phase 7). `cambiar_vista` itself stays unchanged.

**Styling convention**: colors are hardcoded hex strings inline on controls (no theme/constants file) — the recurring palette is cream background `#fbf5e9`, near-black sidebar `#0d0905`, and gold/accent `#f4ca83`. `font_family="Georgia"` with `italic=True` is used for display headings. Match this convention rather than introducing `ft.Theme` or a separate style module unless asked.

**Language**: UI copy, comments, and variable/method names throughout the codebase are in Spanish (e.g. `cambiar_vista`, `vista_actual`, `_crear_boton_menu`). Follow this convention for consistency when adding code.
