## Project overview

"Taku Monky" is an admin panel for a taquería (taco restaurant), built with **Flet** (Python wrapping Flutter). It is one piece of a larger, two-part system:

- **This repo (Python/Flet)**: a desktop admin app for the business owner — manage the menu, view stats, generate content, use an AI agent, etc.
- **Public-facing site (separate, static HTML)**: customer-facing menu page and a table/seating system (`mesas.html`), deployed to Hostinger. It is *not* built from this Python code. As of Phase 4, `index.html`, `menu-platillos.html`, `menu-bebidas.html`, `menu-postres.html`, `style.css`, `catalogo.css`, `catalogo.js`, `menu.js`, and `carrusel.js` (all at the repo root, so the owner can FTP the whole folder as-is) are the real public menu site — wired to live data and verified, but **the owner is still polishing its visual finish himself, so it's not a finished deliverable**; see the dedicated section under Design rules below before touching it. As of Phase 5, `mesas.html` + `mesas.css` + `mesas.js` are a real, browser-tested internal staff tool for registering sales — not a customer-facing QR/table-status system. As of 2026-09-04, it's also being repositioned as the base of a template the developer plans to resell to other restaurants, not just a Taku Monky-branded tool — see the "repintada" note in the dedicated Phase 5 section under Design rules below before touching its visual identity.

**The phased build plan lives in `Hey Claude Code, read this file..txt` at the repo root — read it at the start of a session to know what's done and what's next.** (The owner clears context often; that file is the running roadmap, this file is the stable reference.)

## Design rules (non-negotiable)

This project's visual identity is already established. **Never redesign, re-theme, or "modernize" existing screens while adding functionality.** When wiring up data, change only the data source — the layout, spacing, typography, and colors stay exactly as they are.

When you build something *new* (a dialog, a form, an empty state, an error toast), it must look like it was always part of the app — reuse the same palette, radii, and text styles from the surrounding view:

- **Palette** (hardcoded hex inline on controls; no theme file — keep it that way):
  - `#fbf5e9` page background · `#f8f1de` card/row surface · `#eee5cf` table header · `#eadfca` borders
  - `#0d0905` sidebar / primary button · `#1c1610` and `#18120d` primary text
  - `#f4ca83` gold accent · `#ffa200` and `#e8aa3a` warm accent · `#bf571d` / `#c86a28` orange highlight
  - `#5e5449`, `#7c7267`, `#8a7e72`, `#806f61` muted text · `#b58a6d` section eyebrow labels
  - Status: `#7d8545` green (visible/ok) · `#d9534f` red (destructive)
- **Typography**: display headings use `font_family="Georgia", italic=True` (sizes ~40–48 for page titles, ~15–19 inline). Small uppercase eyebrow labels are `size=11-13, weight="bold"` in `#b58a6d`/`#806f61`. Body text is default font, `size=12-15`.
- **Shapes**: pill buttons `border_radius=30`, cards `border_radius=14-16`, badges `border_radius=12`, icon buttons 30×30 with `border_radius=15` and `ink=True`.
- **Spacing**: views pad `left=36, right=36, top=42, bottom=36`; vertical gaps use `ft.Container(height=N)` spacers rather than margins.

If a design decision isn't already answered by an existing view, ask rather than inventing a new style.

### `views/components/dialogo_platillo.py` (Phase 2.6 — the add/edit form)

`DialogoPlatillo(router, on_guardado, platillo=None)` is a class, not a view — it builds and owns an `ft.AlertDialog` and is opened via `.abrir()` from `menu_view.py`'s "Agregar platillo" button and pencil icons. `platillo=None` → create mode; `platillo=<dict>` → edit mode, prefilled, with an extra red "Eliminar platillo" button (opens a second stacked confirm dialog before actually deleting — Flet supports stacking `show_dialog()` calls). Follows the same card language as `sesion_view.py` (420-wide card, same field styling, same `tight=True` Column gotcha) and the same red error-box styling used there and in `menu_view.py`.

Two things worth knowing if you touch this file:
- **The dialog has an explicit `X` close button (`boton_cerrar`, top-right, positioned via `ft.Stack`).** `AlertDialog(modal=True)` blocks both barrier-tap-to-dismiss and Escape in this Flet version — without an explicit close control there is *no* way to cancel the form once opened. Don't remove it or drop `modal=True` as "simpler"; both are needed together.
- **`_ocupado`/`_set_cargando()` guards `_cerrar()`** so the X can't cut off an in-flight save/delete. Because of that guard, every success path (`_guardar`, `_eliminar_async`) must call `self._set_cargando(False)` *before* `self._cerrar()`, not after — this was a real bug caught during Fase 2.6 verification (the guard was added first, and the success paths silently forgot to clear it, which would have made a successful save appear to hang since `_cerrar()` refused to close). If you add another exit path, keep that ordering.

### `models/cloudflare_storage.py` (Phase 3 — Cloudflare R2 uploads/deletes)

Cloudflare's counterpart to `platillo_dao.py`, and deliberately a **separate file** — this one has nothing to do with Supabase. `validar_y_comprimir()` (Pillow: validates the file is a real image and under 15 MB, corrects EXIF rotation, downsizes to a 1600px longer side, re-encodes WebP quality 80 — same numbers as `EJEMPLOS/lilshop.html`'s `<canvas>` version) and `subir_imagen()`/`eliminar_imagen()` (`httpx`, POST/DELETE to the `taku-monky-uploads` Worker with the admin's Supabase session `access_token` in `Authorization`, same auth pattern as `EJEMPLOS/index.js`) are all **synchronous/blocking**, same convention as `PlatilloDAO` — `dialogo_platillo.py` is the one that wraps each call in `asyncio.to_thread`.

**Reverse-rollback order** (explicit owner requirement, mirrors `EJEMPLOS/lilshop.html`): alta uploads the photo *before* inserting the row, and deletes it if the insert then fails; editing uploads the new photo, updates the row, and only deletes the *old* photo *after* that update succeeds; deleting a platillo deletes the row first (via `PlatilloDAO.eliminar()`) and only then its photo. All three orderings live in `dialogo_platillo.py`'s `_guardar()`/`_eliminar_async()`, not in this module — this file only exposes the pieces.

**Orphan handling — this was the owner's #1 concern for this phase**, from a bad experience on Anxie Store where `EJEMPLOS/lilshop.html`'s `borrarImagenDeR2()` swallows any R2 delete failure into `console.error` and moves on, silently, forever. This project does the opposite by design, decided without re-asking (the owner explicitly delegated the "how"): `eliminar_imagen()` never swallows a failure — it (1) logs the technical detail to console, (2) **appends** a record (filename, full URL, reason, timestamp) to `%LOCALAPPDATA%\TakuMonky\huerfanos_r2.json` (same folder as `sesion.json`, outside the repo, never truncated so older undealt-with orphans aren't lost), and only then (3) raises `LimpiezaImagenFallida`. The caller in `dialogo_platillo.py` reacts differently depending on *when* the failure happens: a rollback-after-a-failed-save just swallows it (nothing was persisted, the orphan log is enough); a cleanup *after* a successful save/delete surfaces a message through `on_guardado(aviso_limpieza)`, which `menu_view.py._on_guardado()` shows via the existing red banner (`_mostrar_error_temporal` — reused as-is, there's no separate "warning" visual language in this project, so the copy itself makes clear the main action already succeeded). If you add a third call site that deletes an R2 image, give it the same two-tier treatment.

`TAMANO_MAXIMO_ORIGINAL` (15 MB) is deliberately generous — it exists to reject genuinely broken input, not ordinary phone photos (the owner's own example was 4 MB originals, which must be accepted and then compressed, never rejected).

### `models/platillo_dao.py` write methods — the RLS silent-failure gotcha

`crear`/`actualizar`/`eliminar`/`cambiar_visibilidad` were added in Phase 2.6. **All three of `actualizar`/`eliminar`/`cambiar_visibilidad` explicitly check that Supabase returned a non-empty `data` and raise `EscrituraSinEfecto` if not — this is load-bearing, not defensive fluff.** Unlike `INSERT`, a Postgres `UPDATE`/`DELETE` blocked by RLS doesn't raise an error: it just matches zero rows and returns HTTP 200 with `data: []`. This was caught live during Fase 2.6 verification — with a session that had no write grant, `cambiar_visibilidad()` returned success and the UI flipped a row's badge to "OCULTO" while the row was still `visible=true` in the real database. If you add another write method here, it needs the same `if not respuesta.data: raise EscrituraSinEfecto(...)` check, or a caller can end up trusting a write that never happened.

New platillos always get `orden = PlatilloDAO._siguiente_orden()` (max existing `orden` + 1) so they land at the *end* of the list — `orden` defaults to 0 in the table, so an insert that omits it would jump to the top.

**Phase 3**: `crear()`/`actualizar()` now also accept an optional `image_url` key in `datos` — included in the row sent to Supabase only when the key is present (so a save with no new photo never touches the column), never required. The actual upload/delete against Cloudflare happens in `models/cloudflare_storage.py`, called from `dialogo_platillo.py` *before* these DAO methods run — this file stays Supabase-only.

**Delete is physically real, and that was audited (2026-08-25)** — the owner asked, having been burned by a previous project. Verified with direct SQL through the Management API (which bypasses PostgREST entirely, so it can't be fooled by an API-layer illusion): the table has **no soft-delete column**, **no DELETE trigger**, and **no rewrite RULE** — `platillos_admin_delete` is a plain RLS policy, and `eliminar()` issues a real `DELETE`. `pg_stat_user_tables` showed `n_tup_del = 5` with gaps in the `id` sequence, i.e. rows the owner deleted from the panel are genuinely gone from Postgres. Edits are equally real: rows the owner edited show `updated_at > created_at`. There is also **no caching anywhere in the panel** — every view refetches on navigation. The one cache is `sessionStorage` in the *public* HTML (Phase 4, `catalogo.js`) — see the dedicated Phase 4 section below for how its freshness is actually kept up to date. It is **not** invalidated by the panel: an earlier draft of this file said it would be, but that's not physically possible — this is a desktop app with no way to reach into a customer's browser, and even Anxie Store's browser-side invalidation only ever cleared the *owner's own* browser, never a customer's. Freshness comes entirely from a short client-side TTL plus active refresh, not from any signal sent by this panel. Dead tuples (38 at audit time, table 64 kB) are ordinary Postgres MVCC and get reclaimed by autovacuum — not a leak, and not worth acting on at this size.

**A real bug was found and fixed here during Phase 4 verification, worth knowing if you touch the cache logic**: the refresh interval fired every 30000ms — the same number as the cache TTL. Markup is a wrapper `<div class="tk-hoja tk-hoja--…">` around an `<img class="tk-hoja-img">`, split across two elements on purpose: the wrapper owns positioning (`left`/`right`/`top`/`bottom`, unaffected by any `transform`) and the wind-sway animation with `transform-origin` set to that leaf's own anchor corner, while the mirror transform lives on the inner `<img>` at the default center origin — one element can't do a center-pivoted mirror and a corner-pivoted rotation at the same time with a single shared `transform-origin`. `pointer-events: none` throughout so the leaves can never block the hero's buttons or the carousel's cards/arrows; `z-index: 1`, above `.tk-cf-fondo` (0) but below both `.tk-hero-contenido` and `.tk-cf-envoltura` (2 and 10). **Animation is a plain always-on CSS loop, not scroll-reactive** (reverted 2026-08-28, same day as the paragraph above — the owner tried scroll-reactive first, then asked to undo it): `@keyframes tk-viento` runs continuously and unconditionally on all 4 `.tk-hoja` (still just gated by `@media (prefers-reduced-motion: no-preference)`), with no JS and no class toggling involved — `index.html` no longer has an `iniciarHojas()` or any `scroll` listener. It was briefly scroll-reactive in between: a `scroll` listener added `.is-swaying` on scroll and removed it via a debounce once scrolling stopped, with the keyframes only applying to `.tk-hoja--*.is-swaying` and shorter 2.6-3.3s durations (sized for a brief scroll burst, not a full cycle). The owner asked to remove that gating because on non-smooth/discrete scrolling (mouse-wheel notches, a choppy trackpad) the scroll events arrive in separate bursts, so the sway kept starting and stopping instead of running continuously — it read as "trabada" (stuck/janky), the opposite of the intent. Durations went back to the original 7-9s (a continuous loop needs a slower cycle to read as an ambient breeze rather than nervous twitching), and `.tk-hoja` dropped its `transition: transform .4s ease` — that existed only to smooth the snap back to rest when `.is-swaying` was removed, which no longer happens since the animation never stops.

**Hojas — live-tuned against an owner reference image (same day, 28 ago 2026, after the paragraph above shipped)**: the owner attached a mockup and iterated live in four rounds, each verified against a real Playwright screenshot/geometry, not eyeballed:
1. **Size**: both pairs were topping out below the intended size (`--hoja-tam`'s old `clamp()` max was reached before the `vw` component could grow further). Retargeted to ~24% of viewport width — specifically the *visible rotated footprint* (`getBoundingClientRect`), not the unrotated `--hoja-tam` — since that's what "occupies 24% of the screen" means to the eye. New `clamp()`s land both pairs at ~24.0vw at 1920px.
2. **Hero vertical bleed**: `-0.36×tam` sat too far below the hero buttons; came down to `-0.15` then, after a Pillow-measured check found one real (non-transparent) frond pixel still dipping ~0.074×tam into section 2, down again to `-0.07`. Horizontal bleed (`-0.30×tam`) untouched throughout.
3. **Menu angle**: `84deg` was already mathematically correct per the original spec (PCA on the alpha mask puts the artwork's own stem→tip axis at -49.06°, so `-49.06+84=34.94°` below horizontal — the same shallowness as the hero, just mirrored) — but the owner wanted it flatter than that spec called for, "tipo `-`". Lowered to `64deg` (≈14.94° below horizontal).
4. **Menu horizontal bleed**: at the flatter angle, the bare rachis (the leafless stem shaft before the fronds start) became visible inside the viewport instead of staying hidden the way it was at the steeper angle. Measured, by sampling perpendicular width along the stem→tip axis, exactly where the fronds start fanning out (~13% of the axis length), then solved for how far to push `left`/`right` (`-0.08×tam` → `-0.22×tam`) so that point lands just past the screen edge — same "hidden rachis" look the hero already had from its larger bleed.

Exact numbers, formulas, and the geometry behind each one live in `style.css` right above the `.tk-hoja--*` rules (comments "AJUSTE 5" through "AJUSTE 8") — read those, not just this summary, before touching size/angle/position again.

**Mobile section 2 has no decorative leaves, and that has now been decided twice (2026-09-04, Phase 4.5)** — there are still exactly **4** `.tk-hoja` accents (hero pair + desktop carousel pair), never 6. A full pair for `.tk-carta-seccion`'s top corners was built, verified and shown to the owner, who answered "quita esas hojas de la sección 2"; everything was removed — markup, rules, wind animation, and the `overflow-x: clip` that existed only for their bleed. This was the second such request and the second removal (the first was 2026-09-03's "intento 3"), so **don't add leaves there on your own initiative.** If the owner asks a third time, `style.css`'s "Las hojas en celular" block at the end of the file carries the full list of already-measured traps so the work isn't redone from scratch: `.tk-hoja--menu-izq/der` can't be recycled (they live in the 3D carousel, `display:none` on mobile — new markup is required inside `.tk-carta-seccion`); the `transform-origin` must be the **bottom** corner, where the crop's stem starts, or a 64deg rotation sweeps the leaf nearly a full height sideways and off-screen; `top: -1.14×tam` follows from the crop being `1.135×tam` tall; every new `.tk-hoja` needs an explicit `width: var(--hoja-tam)` or the div collapses to the PNG's intrinsic 273px; the section needs `position: relative` and `.tk-carta-envoltura` needs `position: relative; z-index: 2`; the side bleed forces `overflow-x: clip` (never `hidden`) or the document grows wider than the viewport; and the clash with the "MENÚ" eyebrow depends on viewport **height**, not width — at 360×640 the leaf's real ink overlapped it (`dx=-41, dy=-9`) and needed a `@media (max-height: 780px)` size drop.

The owner wanted the empty space moved from below the "Ver platillos" button to above the "MENÚ" eyebrow (measured at 393×852: 108.6/116.6 above/below became 161.2/64.0). `flex-end` is the right lever precisely *because* the section is `min-height`, not `height`: when the content is taller than the viewport (360×640 → 743px) there is no spare space to redistribute and the result is byte-identical to before, with no overflow and no photo riding up over the hero — which a fixed height, a `margin-top` or a `translate` would all cause. Verified pixel-for-pixel that desktop (1440/1280) renders identically and that the tablet range's boxes are numerically unchanged.

### Sistema de mesas (Phase 5 — `mesas.html` / `mesas.css` / `mesas.js`, built 2026-09-04)

> **Schema, RLS, and the browser/Flet UI are now all confirmed working end to end (2026-09-04).** Beyond the usual Management-API DDL check, this phase was also verified through the *actual* Supabase Auth REST endpoint (`/auth/v1/token?grant_type=password` with the real admin password) followed by the exact PostgREST calls `mesas.js` makes with the resulting session token — confirming `anon` gets 0 rows on `SELECT` and a 401 RLS violation on `INSERT`, while the logged-in admin can create a `venta`, add a `venta_item`, trigger `updated_at`, close the sale, and cascade-delete cleanly. Phase 5.1's `mesas`/`MesaDAO` got the same treatment (raw REST cross-reference logic plus a live call through `models/mesa_dao.py` itself). On top of that, the developer clicked through the real thing themselves — the login form, `mesas.html`'s fixed table list, and the "Mesas" screen in the actual Flet window all confirmed working. **Still explicitly not a finished, polished deliverable** — see "LO QUE ESTA FASE NO INCLUYE" in the roadmap `.txt`'s Phase 5 block for what's deliberately left out (no sales-history view, no QR/status-board, the AI agent itself), and treat anything not called out as verified there with normal caution.

**What this is, and what it deliberately is not**: a staff-facing order-entry tool — pick/type a table, add real menu items, close the sale — not a customer-facing QR ordering system and not a simple table occupied/free status board. Both alternatives were considered and explicitly ruled out. The `ventas`/`venta_items` schema is documented above near the `platillos` schema paragraph; this section covers the page itself.

**Fully self-contained, on purpose — shares nothing with `catalogo.js`/`style.css`.** It gets its own Supabase client, following `EJEMPLOS/lilshop.html`'s reference pattern (Supabase Auth `signInWithPassword` against the same `ADMIN_EMAIL`, not a bare anon-key read) rather than anything in `catalogo.js`. **It also passes `auth: { persistSession: false }` — reversed on 2026-09-05, and this file used to say the opposite** ("a login-gated internal tool that *needs* a real, persisted session so staff aren't forced to re-login constantly"). The owner asked for the reverse: opening or reloading `mesas.html` must always ask for the password, because it's an internal tool that shouldn't sit logged in on anyone's phone. The change also invalidated every session already stored in every staff browser without touching a single device — which was the only way to do that, since a stored session lives in each browser's `localStorage` and nothing server-side or in this repo can reach it. **`autoRefreshToken` stays ON** (only `persistSession` was turned off): the access token lasts 3600s, and without renewal a tab left open through a shift would start failing on its own after an hour. The goal is that a session doesn't *survive a reload*, not that it dies while in use. This is a different reason from `catalogo.js`, which disables auth wholesale over the Tracking-Prevention/`localStorage` problem documented there; here there is a real login, it just isn't written to disk. Verified live (Playwright): login works and loads the tables, `localStorage` holds **zero** keys afterwards, and both a reload and a fresh tab come back to the login screen. `mesas.css` stays decoupled from `style.css` (no `<link>`) for the reason it always was — this page has no navbar/hero/footer/sidebar to reuse, and staying decoupled means the owner's ongoing hand-polish of the public menu pages (see the Phase 4 warning above) can never accidentally affect this tool, or vice versa. `escapeHtml`/`formatearPrecio` are copied from `catalogo.js` verbatim rather than shared via an import — there's no build step in this repo to share code between independent `<script src>` files across pages that otherwise have nothing in common.

**Palette repainted 2026-09-04 — no longer Taku Monky's cream/gold, on purpose.** `mesas.css` *used to* duplicate `style.css`'s cream/gold hex values (same numbers, same names) so this tool still read as "part of the same brand" despite being decoupled. That's gone: the developer is repositioning this system as the base of a template to sell to other restaurants, not just an internal Taku Monky tool, so it needed to stop looking like *this specific taquería's* brand. `mesas.css` now uses a neutral black/white/gray ("zinc") scale with no relationship to `style.css`'s tokens at all. Simpler to ship and matches this project's existing convention of computing in the app layer rather than in triggers (e.g. `PlatilloDAO._siguiente_orden()`), at the cost of `ventas.total` only being as correct as the last successful write — a future reconciliation job or check constraint is a reasonable hardening step, not done here.

**Why this got built now**: mainly to unblock Phase 6. The AI agent needs real sales data to be useful — today only `platillos` exists — so this is what generates that data.

### Agente de IA (Phase 6 — `views/agenteIA_view.py` + `models/ia_controller.py` + `models/venta_dao.py`, built 2026-09-05)

Same pattern as `EJEMPLOS/ia_controller.py`: a DAO reads real rows, they get flattened to text, that text goes into the system prompt, then the model is called. There is no `ANTHROPIC_API_KEY` in `.env` and none is needed. **It was `gpt-4o` until 2026-09-05 and this file used to say so** — the developer switched it the same day for cost: building and testing the agent burned ~$0.15 of a $4.50 OpenAI balance in one session, and `gpt-4o-mini` is roughly 15–20x cheaper per token. Retested live after the swap: the sales question copies the precalculated figure exactly (`Mesa 1 · $1,206`, byte-identical to `_resumen_calculado`'s row) and the scope rule still rebounds an off-topic question. **What actually makes the cheaper model safe here is that Python does the arithmetic** — see the `_resumen_calculado` paragraph below; the model only copies numbers, it never sums.

**`models/venta_dao.py`** (new) — `VentaDAO`, read-only on purpose: writing a `venta`/`venta_item` is `mesas.js`'s job (see the Phase 5 section above), never the panel's. `obtener_ventas()` / `obtener_items_de_ventas(ids)` / `obtener_ventas_con_items()` (the two joined in Python, each venta getting an `items` list embedded) follow the same no-`select('*')`, no-caught-exceptions convention as `platillo_dao.py`/`mesa_dao.py`. Capped at 500 ventas per call — not real pagination, just a guard so the prompt sent to OpenAI doesn't grow unbounded as the business accumulates months of sales; at today's volume (single digits) it doesn't cut anything. If the real volume ever approaches that cap, the fix is summarizing/filtering by date in SQL, not raising the number.

**`models/ia_controller.py`** (new) — `IAController.preguntar(pregunta, historial=None)`. Builds the system prompt from the 4 tables flattened to text, plus the current local date/time (Supabase's UTC timestamps are converted to local time first, same reasoning as `_tiempo_relativo()` in `home_view.py`, so the model can answer "today"/"yesterday" correctly instead of working off raw UTC). `historial` is an optional list of prior `{"role", "content"}` turns — `agenteIA_view.py` accumulates it so the agent has memory within one chat session; nothing persists it beyond that (same "no view keeps state across visits" rule as the rest of the app). No caching anywhere: every question re-reads all 4 tables, matching the project's established "no hidden cache in the panel" rule (see the delete-audit note under `platillo_dao.py` above) — cheap at this data volume. The agent is explicitly told it's **read-only**: it can't open/close a sale or edit the menu, and is instructed to say so if asked, rather than pretend to act.

**Las sumas las hace Python, NO el modelo (2026-09-05, `_resumen_calculado`) — y se agregó por un fallo REAL, no por prudencia.** El prompt lleva una sección `TOTALES YA CALCULADOS` con los totales por periodo (hoy/ayer/esta semana/este mes), por mesa, por día y por producto, ya sumados en Python, y una regla que le dice al modelo que los **copie tal cual y no vuelva a sumar la lista a mano, ni para verificar**. Motivo, medido contra la base real con **8 ventas nada más**: a la pregunta "¿cómo me fue por mesa esta semana?" `gpt-4o` se saltó una venta entera al sumar (contestó **$1,587** en la Mesa 1 donde eran **$2,127**, o sea $540 perdidos), sin avisar de nada y con el resto de la respuesta impecablemente redactada — el peor tipo de error posible para un panel que el dueño le va a enseñar a su contador. Con el resumen precalculado, la misma pregunta contesta $2,127. Agrupar y sumar listas es exactamente lo que un LLM hace mal; si con 8 ventas ya fallaba, con meses de operación es peor, así que **no quites esa sección ni "simplifiques" el prompt quitándole la regla de los números**. Y desde el 2026-09-05 pesa todavía más: el modelo por defecto pasó a `gpt-4o-mini`, que es más barato pero peor en aritmética que el `gpt-4o` que ya fallaba — esta sección es justo lo que hace que ese cambio no cueste precisión. **Los desgloses por mesa y por producto van repetidos por periodo** (hoy / ayer / esta semana / histórico, vía `_bloque_desglose`), no una sola vez en histórico: la pregunta natural del dueño es "¿cómo me fue HOY por mesa?", y con un único desglose histórico el modelo tendría que volver a filtrar y sumar a mano — justo lo que esto existe para evitar. Las **cuentas abiertas** se reportan aparte, con su mesa y su monto, y el resumen dice explícitamente que ese dinero no está cobrado ni incluido en ningún total; sin eso el agente inflaría la venta del día con las mesas que siguen comiendo. Detalles de conteo, ya decididos: solo cuentan las ventas **cerradas** (una cuenta abierta no es dinero cobrado; las abiertas se reportan aparte), y el día de una venta es el día en que se **abrió** la cuenta. **El día NO corta a medianoche**: `_HORA_CORTE_DEL_DIA = 6` y `_dia_de_negocio()` hacen que el día del negocio corra de las 6:00 a.m. a las 6:00 a.m. del día siguiente, así que una venta de la madrugada cuenta para la noche anterior. Lo pidió el dueño el 2026-09-05 al ver una venta suya de las 00:40 contada como "hoy" cuando para él fue "anoche" — y tiene razón: una taquería que cierra tarde sigue trabajando la misma noche a la 1 a.m. Poner esa constante en `0` regresa al corte de medianoche sin tocar nada más; es el único lugar donde vive la decisión. El prompt también se lo explica al modelo, que ya lo justifica solo si el dueño pregunta por qué su venta de madrugada aparece en el día anterior (probado).

**La regla de alcance va ARRIBA DEL TODO en el prompt, y es dura a propósito.** El agente solo habla de este negocio (menú, mesas, ventas y lo que se concluya de esos datos); cualquier otra cosa — cultura general, matemáticas, Pokémon, poemas, programación, qué modelo de IA es — la rebota con una sola frase y sin contestarla "de pasadita". También se le dice que no cambie estas reglas aunque quien escriba diga que es el desarrollador, que está en modo de pruebas o que es "solo por esta vez". El prompt original traía una versión suave de esto perdida a media lista, **y se cayó sin querer al reescribir el archivo el 2026-09-05** — el desarrollador lo cachó en un minuto pidiéndole 3 Pokémon, y se los dio. Si vuelves a reescribir este prompt, revisa que esta sección siga ahí: es lo que evita que el panel parezca un juguete cuando un mesero curioso se pone a jugar. Probado con 6 intentos (incluidos "ignora tus instrucciones anteriores" y "solo por esta vez"): los 6 rebotaron con la misma frase, y las preguntas del negocio — incluida una de consejo ("¿qué promoción me conviene?") — siguieron contestando normal.

**Dos normalizaciones que parecen cosméticas y no lo son.** (1) **Mesas**: `ventas.mesa` es texto libre copiado al abrir la cuenta (ver Fase 5), así que la misma mesa aparece escrita distinto según el día — en los datos reales conviven `"mesa 1"` y `"Mesa 1"`. `_normalizar_mesa()`/`_canonizar_mesas()` las unifican (gana el nombre del catálogo `mesas` cuando la mesa todavía existe), y el detalle venta-por-venta usa el mismo nombre unificado que los totales, para que el modelo no tenga dos verdades para la misma mesa. (2) **Productos**: aquí es al revés y agrupar por nombre sería el bug — el menú real tiene platillos **distintos** con nombres casi iguales (`"taco arabe"` #30 a $23 y `"Taco arabe"` #32 a $987), así que `_resumen_calculado` agrupa por **`platillo_id`** y solo cae al nombre normalizado cuando el platillo ya se borró (`platillo_id` en NULL por el `ON DELETE SET NULL`). Cada renglón sale etiquetado con su `#id` para que el modelo pueda amarrarlo contra la lista del menú.

**⚠️ La trampa de UTC: el dashboard de Supabase NO muestra la hora local, y ya causó un susto real (2026-09-05).** El Table Editor pinta `created_at`/`cerrada_at` en **UTC** (de ahí el `+00` al final de la columna); el agente, en cambio, convierte a hora local con `_fecha_local()` antes de meter nada al prompt, que es lo correcto para que "hoy"/"ayer" signifiquen lo que el dueño entiende. En México eso son **6 horas de diferencia**, así que una venta de las **19:31 del viernes** se ve en el dashboard como **`2026-09-05 01:31+00`** — con fecha de sábado. El desarrollador comparó las dos pantallas, vio "5 de septiembre" en Supabase y "4 de septiembre" en el agente, y dio por hecho que el agente estaba roto. **No lo estaba.** Antes de "arreglar" una discrepancia de fechas: comparar `datetime.now()` contra `datetime.now(timezone.utc)` y hacer la resta — lo aclara en dos renglones. Lo que sí conviene, si vuelve a pasar, es enseñarle al dueño la conversión, no cambiar el código.

**`views/agenteIA_view.py`** — the skeleton (fake echo of whatever the owner typed, no real call to anything) became real. El texto del agente cae directo sobre el fondo de la vista, como en Claude/ChatGPT — el desarrollador lo pidió con una captura de Claude al lado. Cómo está hecho, que es justo lo que evita romper la secuencia: el `ft.Container` de `_burbuja_ia()` **sigue ahí** (dentro de su `_fila()`, con su `HUECO_IA` y su `ft.ScrollKey` intactos), solo se le quitaron `bgcolor`, `border` y `border_radius`. **No se pinta `bgcolor="#fbf5e9"` a mano**: un Container sin `bgcolor` ya deja ver el fondo, y así no hay un segundo lugar que actualizar si el fondo cambia. Lo que **sí** hubo que tocar además del color es el **padding horizontal, de 18 a 0** — sin superficie que lo justificara, ese hueco dejaba el texto de la IA sangrado 18 px respecto al borde izquierdo de la conversación y respecto al "Pensando..." que aparece justo antes en ese mismo sitio (ese nunca tuvo padding propio). El **vertical se queda en 12**, y eso es a propósito: sumado al `spacing=18` de `lista_mensajes` da exactamente el mismo aire entre mensajes que había con burbuja, o sea que quitarla no movió nada de sitio. La del usuario era dorada (`#f4ca83`, rellena y sin borde) y el desarrollador la igualó a la de la IA el mismo día porque esa ya se veía "simple y minimalista"; **no le devuelvas el dorado sin que lo pida**. Consecuencia a tener presente: **quién habla se distingue por tres cosas y ninguna es el color del texto** — tener burbuja o no tenerla, el lado, y el ancho máximo (`alignment` + el padding contrario, `HUECO_USUARIO=170` / `HUECO_IA=70` — ver el punto del ancho en el párrafo de la secuencia de chat). Las cajas de tabla/cita/código del markdown (`#f3ead4`) ahora caen sobre `#fbf5e9` en vez de sobre `#f8f1de`: se despegan un punto más, y se vieron bien en la ventana real antes de dar esto por cerrado. **La caja de texto es la única de las tres que se realza, y ese realce depende del estado de la pantalla y del foco — `_aplicar_realce_caja()` es el único lugar donde vive esa decisión.** Mueve dos cosas juntas, sombra y color del borde:

La sombra es blur 10 / spread 0 / **7%** de negro / offset (0,2). Llegó ahí en tres pasos el mismo día (2026-09-05), y conviene conocerlos antes de tocarla: era una nube (blur 24 / spread 1 / **30%** / offset 0,7), el desarrollador la mandó quitar del todo junto con el dorado de la burbuja, vio la caja completamente plana al lado de un chat de verdad y pidió regresarla *"pero no tan exagerada"* y **sin quitarle el borde**; después notó que en los chats grandes el realce **no está siempre encendido sino que responde al foco**, y que ahí también se oscurece el borde. El límite sigue siendo el mismo: se tiene que notar solo cuando la buscas — literalmente por eso el desarrollador no se había dado cuenta de que la caja de Claude Code lleva una.

Tres detalles que cuestan si se rompen:
- **El borde de BIENVENIDA también reacciona al foco, y eso se decidió en dos pasos.** Primero se dejó fijo en `#eadfca` porque el desarrollador había dado ese estado por cerrado (*"esa ya quedó chevere y muy profesional"*); minutos después se fue a mirar la caja de Claude Code, vio que ahí también se oscurece, y pidió el mismo comportamiento. Lo que **no** cambió es la sombra: en bienvenida sigue siempre encendida. Verificado en la ventana nativa comparando las capturas entre sí — al enfocar cambia solo el contorno de la caja (delta 38 en el canal azul, exactamente `202→164` de `#eadfca` a `#d8c3a4`) y al desenfocar vuelve **píxel por píxel idéntica** a como se ve al abrir la pantalla.
- **⚠️ El `TextField` va SIN relleno (`filled=False`, sin `bgcolor`) y eso es load-bearing: el fondo lo pinta `caja_entrada`.** Un `TextField` con relleno se dibuja **encima del borde** del Container que lo envuelve, y como `caja_entrada` no tiene padding a la izquierda, se comía el tramo central del borde izquierdo: la píldora salía con las curvas de arriba y de abajo pero con un **hueco en medio**. El desarrollador lo vio a simple vista ampliando la esquina; se confirmó renderizando tres variantes lado a lado en la ventana real (con relleno / con padding izquierdo de 2 px / sin relleno) y solo la tercera cierra el contorno. **No le pongas `bgcolor` "para que combine"** — es exactamente el bug. De paso esto vuelve innecesarios el `focused_bgcolor`/`hover_color` que antes se fijaban al mismo tono: Material oscurece el *relleno* al enfocar o al pasar el mouse (medido: `#f8f1de` → `#eee8d5`) y, como los botones le quitan 72 px a la derecha, esa franja se quedaba del color original y la píldora se veía partida en dos tonos; sin relleno no hay nada que oscurecer. Verificado después del cambio: al enfocar cambia **solo el contorno** de la caja, el relleno se queda en `#f8f1de` en los cuatro estados. Efecto lateral aceptado: el texto quedó **4 px más a la izquierda**, porque ahora manda el `content_padding=24` declarado en vez del padding implícito que Material añadía; no se compensó para no mover los ~74 caracteres por renglón que `_lineas_estimadas()` tiene medidos.
- **El `border_radius=35` NO era el problema, aunque lo parezca.** Primero se diagnosticó como un radio mayor que la mitad del alto de la caja (60 px) y se bajó a 31; renderizando el contorno con radios 31/30/29/28/26 se comprobó que **los cinco daban exactamente el mismo hueco**, o sea que la forma no tenía nada que ver. El radio volvió a 35 y ahí se queda.
- **El realce depende del foco y NO de si hay texto escrito** (pedido así, explícitamente). Verificado con clics reales en los cuatro cruces: vacía sin foco / vacía con foco / con texto y foco / **con texto pero sin foco** — este último es el que delataría una implementación que se colgó del contenido en vez del cursor.
- **⚠️ Un `focus()` programático NO dispara `on_focus`** — medido en la ventana real, y tampoco en web (o sea que no es el mismo asunto que la nota del foco más abajo, que sí es solo del cliente web). Por eso el `finally` de `_responder` pone `self._entrada_enfocada = True` a mano después de `await self.entrada.focus()`: sin eso la caja se quedaba plana con el cursor ya dentro, lista para escribir pero sin verse así, hasta que el dueño hiciera clic. Deshabilitar el campo, en cambio, **sí** dispara `on_blur` de verdad (también medido), y de ahí sale un comportamiento que no se programó pero se quedó por bueno: mientras la IA piensa la caja se ve plana —no se puede escribir— y se vuelve a realzar sola al devolver el foco. A failure (missing `OPENAI_API_KEY`, no internet, etc.) renders in the same `#f7e4e3`/`#d9534f`/`#a33c39` banner already used elsewhere instead of crashing the view. Palette and typography were not touched; the **layout was**, the same day — see the next paragraph.

**Secuencia de chat (2026-09-05, mismo día que la Fase 6) — la pantalla tiene DOS estados y ya no uno solo.** Como quedó al cablearla, el saludo, los mensajes y la caja de texto vivían todos en la misma columna centrada, así que cada mensaje nuevo empujaba la caja hacia abajo y las burbujas se amontonaban encima de ella. El desarrollador lo señaló con un video de Claude como referencia y pidió *"la secuencia que tienen las grandes IA"* — explícitamente **solo la secuencia**, nada de iconos de adjuntar/cambiar modelo, "a lo mucho el icono de desplegar mensaje". Lo que hay ahora: **BIENVENIDA** (saludo Georgia + caja, centrados con dos `ft.Container(expand=True)` que se reparten el hueco) y **CONVERSACIÓN** (`zona_conversacion` de 720 px con su propio scroll arriba, caja anclada abajo). `_montar_bienvenida()`/`_montar_chat()` reescriben `self.raiz.controls`; el cambio ocurre **una sola vez**, en el primer mensaje. Detalles que no se ven pero cuestan si se rompen:
- **El ancho de la conversación es el mismo 720 de la caja** (`ANCHO_CHAT`, una constante para las dos) para que las burbujas queden alineadas con sus bordes. Cada mensaje va en un `ft.Container` con `alignment` a un lado y **padding del lado contrario** (`HUECO_USUARIO=170` / `HUECO_IA=70`): ese padding es el tope de ancho de la burbuja — sin él, `flet` le da restricciones sueltas y una respuesta larga se estira los 720 completos.
- **`auto_scroll` está APAGADO a propósito**, y no es un olvido: dejaría la vista al final de la respuesta, que en una respuesta larga significa aterrizar en el último renglón. En su lugar cada pregunta lleva un `ft.ScrollKey` y `_ir_a()` hace `scroll_to(scroll_key=...)`, que la deja **hasta arriba** con la respuesta empezando desde su primer renglón (verificado con una respuesta más alta que la pantalla). `flet` exige `auto_scroll=False` para que `scroll_to()` sirva, y `scroll_to()` **no funciona en `ListView`/`GridView`** (construyen sus hijos por demanda) — por eso la conversación es una `ft.Column` con `scroll`, no una `ListView`. El `asyncio.sleep(0.08)` antes del desplazamiento tampoco sobra: sin él el cálculo sale con la lista todavía sin el mensaje recién agregado.

Probado con teclado de verdad, no leyendo el código (ver la nota de verificación abajo). ⚠️ Este párrafo decía que era obligatorio "porque **no hay botón de enviar**" — desde el 2026-09-05 sí lo hay (ver la sección del botón de enviar abajo), así que Enter ya no es la única salida; aun así **no lo cambies a que Enter meta el salto y Shift+Enter mande**: el dueño ya aprendió el comportamiento actual y el botón se pensó como un camino más, no como el reemplazo del teclado.

Ese ancho por carácter es del tipo de letra, no de la caja, así que sigue valiendo aunque el campo se angoste: lo que cambia es cuántos caben por renglón (**~74 desde que entró el botón de enviar, ~79 antes**). Este botón **arrastró un bug desde que se construyó hasta el 2026-09-05**: nunca llegaba a mostrar `UNFOLD_LESS` — ver la trampa de `ft.Icon.name` abajo.
- **`focused_bgcolor`/`hover_color` fijados al mismo `#f8f1de` que `bgcolor`**: Material oscurece el fondo del campo al enfocarlo (medido: `#f8f1de` → `#eee8d5`). Antes no se notaba porque el campo ocupaba toda la píldora; ahora que los botones le quitan 72 px a la derecha (30 + 34 + los dos huecos de 4; eran 42 con un solo botón), esa franja se quedaba del color original y la caja se veía partida en dos tonos.

- **⚠️ El hueco entre trozos se reparte a mano, y es lo único que sostiene el cambio.** Una sola `ft.Markdown` mete su `block_spacing` entre bloques y **nada** entre los renglones de un mismo párrafo (los saltos suaves). Partida en controles ese reparto se pierde, así que cada trozo se devuelve con su hueco: `ESPACIO_BLOQUE` cuando abre bloque nuevo (hubo línea en blanco, o es título/lista/tabla/código/cita) y 0 cuando solo continúa el párrafo de arriba. Los renglones de **lista cuentan como bloque** — flutter le mete su `block_spacing` a cada viñeta, así que sin esa regla las listas salían 12 px más juntas que antes; se cachó **midiendo**, no leyendo. `ESPACIO_BLOQUE` es constante justo porque ahora hay dos sitios que lo necesitan (`_estilo_markdown()` y el partidor); escrito a mano en cada uno, un cambio dejaría al otro atrás.
- **Verificado píxel por píxel, no "se ve igual"**: la respuesta partida y la entera se renderizaron a 650 px (el ancho real de la conversación) y `ImageChops.difference` dio **bbox `None`** — idénticas — con una muestra que traía título, párrafo, tabla con pipes, **tabla sin pipes en los extremos** (GFM las permite y el modelo puede contestar así; se reconocen por la fila de guiones, no por el pipe inicial), negritas, viñetas, **viñetas anidadas** (un renglón sangrado se pega al trozo de arriba: suelto perdería la sangría, y con 4 espacios flutter lo pintaría como bloque de código), lista numerada, saltos suaves, cita, regla horizontal y código. **Si tocas el partidor, ésa es la prueba que hay que repetir.**
- **Al terminar, la columna de renglones se cambia por UNA sola `ft.Markdown` con la respuesta completa**, y eso no es limpieza: es lo que devuelve la **selección de texto de punta a punta**. Partida en controles, el dueño solo podría seleccionar dentro de un renglón y copiar una tabla entera —justo para lo que `selectable=True` existe— dejaría de funcionar. El cambio es invisible porque las dos formas pintan lo mismo píxel por píxel (comprobado en la ventana real: el cuadro de antes del cambio y el de después dan `bbox None`), y se hace pasado el fundido del último renglón para no cortarlo.
- **Los tres números van juntos.** `PASO_APARICION` (0.055 s) es cada cuánto **arranca** el siguiente renglón; `DURACION_APARICION` (340 ms) es lo que tarda **uno** en aparecer, y es como seis veces el paso **a propósito**: así siempre hay varios renglones fundiéndose a la vez y se lee "de corrido", que es como se pidió — igualarlos lo convertiría en una fila de parpadeos sueltos. `PASOS_MAXIMOS` (32) es el tope de avisos por respuesta: pasado ése los renglones se revelan de dos en dos o de tres en tres, así que ninguna respuesta tarda más de ~1.8 s en acabar de salir. `SUBIDA_APARICION` solo se le aplica a los renglones de texto: el `offset` de flet se mide en fracción de la altura del propio control, así que la misma fracción que en una línea de 25 px es un empujón de 6, en una tabla de 130 px es un brinco de 32.
- **La lección del logo de "Pensando..." NO aplica aquí, aunque el ritmo se parezca.** Allá python empujaba 14 **cuadros** por segundo y la animación se congelaba con la máquina ocupada; aquí python solo manda el **disparo** de cada renglón y quien interpola el fundido es el cliente (`animate_opacity`). Si un aviso llega tarde, ese renglón arranca tarde pero aparece igual de suave, nunca a medias. Y llega cuando la respuesta **ya está en la mano**, o sea con el proceso desocupado, no mientras se leen 4 tablas y se espera a OpenAI.
- **`_revelar()` corre en su propia tarea**, lanzada desde el `finally` de `_responder`: la caja de texto queda lista para escribir en cuanto llega la respuesta y no espera a que acabe de salir el texto (medido: a los 900 ms la caja ya está habilitada). Los renglones **nacen apagados** en vez de irse agregando de uno en uno, así que la respuesta ocupa su alto completo desde el primer momento y el scroll no da brincos mientras el texto sale. Se comprobó que la animación **no toca el desplazamiento**: la misma respuesta larga, animada y de golpe, deja la conversación en la misma posición (`bbox None`). Y se ejercitaron los tres caminos de `_responder` en la ventana real —respuesta buena, `RuntimeError` y excepción genérica— porque este cambio le movió el `try`/`finally` y ésa es la zona que ya escondió un fallo antes (ver `_quitar_indicador`).

**Las respuestas se pintan con `ft.Markdown`, no con `ft.Text` (2026-09-05, decidido con una comparación a la vista).** `gpt-4o` no contesta en texto pelón: contesta en markdown, y con `ft.Text` esos símbolos salían crudos (`**Mesa 1**`, `###`, y una tabla convertida en un montón de pipes). Se le mostró al desarrollador la misma respuesta pintada de las dos formas y eligió renderizarla. Esto **no toca el prompt de `models/ia_controller.py`** ni lo que el modelo responde — es solo cómo se pinta lo que ya llegaba; la burbuja, sus colores y la secuencia quedaron igual. Tres cosas que no se ven pero sostienen esto:
- **`soft_line_break=True` es obligatorio, no un adorno.** En markdown un solo salto de línea NO parte el renglón, y el modelo a veces contesta listas sin viñetas (`"Mesa 1 — $2,150\nMesa 2 — $1,480"`); sin esto se pegarían todas en un párrafo corrido, que sería peor que el `ft.Text` que se reemplazó. Verificado con ese caso exacto.
- **`extension_set=GITHUB_FLAVORED`** es lo que habilita las tablas (con el set por defecto una tabla se queda en pipes), y de paso trae la regla de GFM de no volver cursiva un guion bajo dentro de una palabra — o sea que si el agente menciona `venta_items` en una respuesta, sale literal.
- **`_estilo_markdown()` es una función, no una constante**: devuelve un `MarkdownStyleSheet` nuevo por burbuja, para no tener que averiguar si `flet` tolera el mismo objeto de estilos colgado de varios controles a la vez. Todos sus colores salen de la paleta ya existente (los tamaños y la fuente sí cambiaron el 2026-09-06 — ver el párrafo de Georgia arriba); el `#f3ead4` de las cajas de tabla/cita/código es el único tono nuevo, y es el `#eee5cf` de los encabezados de tabla de `menu_view.py` un punto más claro para despegarse del `#f8f1de` de la burbuja.

Verificado con capturas de la ventana real en los tres tipos de respuesta que el modelo da: una corta de un renglón (la burbuja se sigue encogiendo, no se estira), varios renglones sin marcas (los saltos se respetan) y markdown completo con negritas, encabezados, viñetas, lista numerada, tabla y cita.

Clicking through the real native window was still pending ese día.

**Sí hay forma de verificar una pantalla de flet con capturas y teclado — este archivo decía lo contrario ("no hay equivalente a Playwright para una ventana nativa de flet") y quedó desmentido el 2026-09-05 al rehacer la secuencia de chat.** Son dos herramientas, cada una para lo suyo, las dos en el scratchpad y sin tocar el repo:
1. **Capturas de la ventana real**: un guion que monta la vista con un `IAController` falso y el `Sidebar` de verdad, la envuelve en **`ft.Screenshot(content=..., expand=True)`** y va guardando PNGs con `await foto.capture(pixel_ratio=1.0)` entre paso y paso. Es el render nativo de verdad (fuentes del sistema incluidas), no una aproximación. ⚠️ `pixel_ratio` tiene que ser **float**: con `1` el cliente contesta `type 'int' is not a subtype of type 'double?'` y la corrutina se queda colgada sin error visible.
2. **Teclado de verdad**: la misma vista servida como app web (`FLET_FORCE_WEB_SERVER=1 FLET_SERVER_PORT=8560`, y `assets_dir="assets"` — con `"."` el servidor sirve el `index.html` del sitio público en vez de la app) y manejada con Playwright. El cliente de flet es el mismo Dart en escritorio y en web, así que Enter/Shift+Enter se comportan igual. **`SendKeys` de PowerShell contra la ventana nativa NO sirve** (se probó: `AppActivate` devuelve `True` y las teclas no llegan a Flutter). Lo único que difiere entre los dos clientes es el `focus()` programático (ver la nota del foco arriba); para eso, en escritorio, se comprueba con los eventos `on_focus`/`on_blur` del propio campo.

## Running the app

```bash
python main.py
```

This launches the Flet desktop app (`ft.run(main, assets_dir=".")` in `main.py`), which opens a maximized native window titled "Taku Monky - Panel" — **always** showing `SesionView` (login) first. Nothing is remembered between launches; see "Why the login is never remembered" below.

`python panel_licencias/main.py` launches a **different, unrelated** window — the developer's own multi-client licence panel, not part of the owner's panel and not reachable from it. See its entry under Architecture below. (It replaced `licencia_admin.py`, deleted 2026-09-05.)

There is no build step, linter, formatter, or test suite configured in this repo (no `pyproject.toml`, no test files). Dependencies are pinned in `requirements.txt` (`flet`, `supabase`, `python-dotenv`, `httpx`, `pillow`, `rembg`, `openai`) and installed in the active Python environment — install with `pip install -r requirements.txt` if a fresh environment is missing any of them (`supabase`/`python-dotenv`/`openai` in particular aren't part of a bare Python install).

**Public site** (`index.html` and the 3 `menu-*.html` pages) has no build step either — it's meant to be uploaded to Hostinger as-is. To preview it locally, serve the repo root as static files (e.g. `python -m http.server 8123`) and open `http://localhost:8123/index.html`; opening the file directly via `file://` can behave differently for `sessionStorage`/`fetch`, so prefer a real (even if local) HTTP origin when testing.

## Architecture

**MVC-ish structure, single window, no real routing:**

- `main.py` — entry point; creates the Flet `Page` and hands it to `MainController`.
- `controllers/main_controller.py` — `MainController` acts as the app's router/state holder (referred to as `router` throughout the view/component code). It owns:
  - `self.vista_actual` — name of the currently active view (`"home"`, `"menu"`, `"agente_financiero"`, `"contenido"`, `"ajustes"`, `"biblioteca"`).
  - `self.view_switcher` — an `ft.AnimatedSwitcher` that swaps view content with a scale transition.
  - `cambiar_vista(vista: str, abrir_dialogo_nuevo: bool = False)` — the *only* navigation mechanism: instantiates the matching view class, sets it as the switcher's content, and rebuilds the `Sidebar` so its active-button highlighting stays in sync. There is no separate router/state-management library. `abrir_dialogo_nuevo` (added Phase 2.7) is a one-shot, non-persisted flag forwarded straight into `MenuView`'s constructor when `vista == "menu"` — it exists only so `home_view.py`'s "Agregar un producto nuevo" shortcut can land on Menú with the add dialog already open. Every other caller (the sidebar, the other atajo, every `cambiar_vista("contenido")` call) omits it and gets the unchanged default behavior — there's no router-level state that could leak into a later, unrelated navigation.
- `views/*.py` — one file per screen (`home_view.py`, `menu_view.py`, `mesas_view.py`, `agenteIA_view.py`, `contenido_view.py`, `ajustes_view.py`, `biblioteca_view.py`). `contenido_view.py` and `biblioteca_view.py` are still placeholder screens — they are **Fase 7**, the content-creation feature, and the only real *function* the project has left (`Fase 8` after it is a cleanup pass — see below). Every view follows the same shape:
  ```python
  class SomeView(ft.Container):
      def __init__(self, router):
          super().__init__()
          self.router = router
          self.expand = True
          self.height = float("inf")
          self.bgcolor = "#fbf5e9"
          self.content = ft.Column(...)  # built inline in __init__
  ```
  Views are rebuilt from scratch on every navigation (no persistent state between visits) and call back into the app only through `self.router` (e.g. `self.router.cambiar_vista(...)`, `self.router.page`).
- `views/components/sidebar.py` — `Sidebar(router)` is the persistent left nav (also takes `router` and reads `router.vista_actual` to highlight the active item). Includes a hardcoded WhatsApp support link.
- `views/components/dialogo_platillo.py` — `DialogoPlatillo`, the add/edit form dialog used by `menu_view.py` (Phase 2.6; gained the photo picker in Phase 3). See the dedicated sections under Design rules above — it's not just a form, it has several non-obvious gotchas (the explicit close button, the `_ocupado` ordering, the Tkinter file picker, the upload/rollback order) worth reading before touching it. Also exports a module-level `_confirmar(page, *, titulo, mensaje, on_confirmar)` helper (the generic destructive-action confirm dialog) — `mesas_view.py` imports and reuses it as-is rather than duplicating it, despite the leading underscore; it has no dependency on anything platillo-specific.
- `views/mesas_view.py` + `views/components/dialogo_mesa.py` (Phase 5.1, added 2026-09-04) — the panel screen where the owner manages the fixed table catalog (`public.mesas`: add/rename/delete) that `mesas.html` reads to show each table's status. `DialogoMesa` is a deliberately trimmed-down `DialogoPlatillo`: same visual language (420-card, same field/button/error styling, same explicit-X-button + `_ocupado` guard gotcha) but a single `nombre` field, since a mesa has nothing else. `MesasView` itself is a shrunk `menu_view.py` — no search, no columns, just a name + edit/delete per row — and reuses `_confirmar` from `dialogo_platillo.py` for the delete confirmation instead of writing a second copy.
- `models/` — the data layer:
  - `supabase_client.py` — the one shared `Client`, created with `SUPABASE_ANON_KEY` via `create_client()`. Write access comes from whatever session is active on `client.auth`, not from the key. Also exposes `SUPABASE_ADMIN_EMAIL` (read from `.env`) so `SesionView` can prefill the email field.
  - `sesion.py` — **deleted 2026-09-05, don't bring it back.** It used to persist the session (access_token/refresh_token/expires_at, never the password) to `%LOCALAPPDATA%\TakuMonky\sesion.json` and restore it at startup. See "Why the login is never remembered" below for why that had to go. Nothing writes to that folder now except `cloudflare_storage.py`'s orphan log, which creates it on demand.
  - `platillo_dao.py` — `PlatilloDAO`, a DAO class following the `VentaDAO` pattern from `EJEMPLOS/ia_controller.py`. `obtener_todos()` (Phase 2.1-2.5): a blocking `client.from_("platillos").select(...)` call, `select()`-ing only the columns `menu_view.py` paints (`id, nombre, descripcion, categoria, precio, visible, image_url` — never `select('*')`, same rule as `EJEMPLOS/catalog-cache.js`), ordered by `orden` then `id`. `crear`/`actualizar`/`eliminar`/`cambiar_visibilidad` (Phase 2.6) round out the CRUD — see the dedicated "RLS silent-failure gotcha" note under Design rules above before touching any of them; `crear`/`actualizar` gained an optional `image_url` in Phase 3. `obtener_estadisticas()` and `obtener_recientes()` (Phase 2.7) back `home_view.py`'s two dynamic cards — the former makes 4 `count="exact", head=True` requests (1 total + 1 per fixed category), all filtered to `visible = true`, and never downloads row data; the latter selects `id, nombre, created_at, updated_at` ordered by `updated_at desc` and leaves the Nuevo/Editado interpretation to the view, not the DAO. None of the methods in this file catch exceptions themselves; failures are left to rise to the caller (`menu_view.py`/`dialogo_platillo.py`/`home_view.py`, via `asyncio.to_thread`), same division of labor as `sign_in_with_password` in `sesion_view.py`.
  - `cloudflare_storage.py` (Phase 3) — compresses (Pillow → WebP) and uploads/deletes platillo photos against Cloudflare R2 through the `taku-monky-uploads` Worker (`httpx`). See the dedicated section under Design rules above — in particular the orphan-logging behavior (`huerfanos_r2.json`) and the reverse-rollback order, both explicit owner requirements for this phase.
  - `configuracion_negocio_dao.py` (Phase 5.3) — `ConfiguracionNegocioDAO` for the one-row licence table (see the schema paragraph above): `obtener()` (raises rather than returning `None` when there's no row — an empty table is a sign someone deleted it by hand, not a state the UI should render nicely) and `actualizar(datos)`, which writes only the keys present in `datos` out of `nombre`/`fecha_inicio`/`fecha_fin`/`activo` and carries the same `EscrituraSinEfecto` guard as the other DAOs. **Nothing imports it right now** — its only importer was `licencia_admin.py`, deleted 2026-09-05. It's kept on purpose rather than by oversight: it is the piece the licence lock will need to *read* `activo` from the owner's app (the owner still has SELECT on that table, just no longer INSERT/UPDATE/DELETE). Its `actualizar()`, by contrast, is now dead weight — the owner can't write there, and the one who can is `panel_licencias/licencia_dao.py`, which is a separate instantiable copy because it juggles N projects.
  - `tiempo.py` (2026-09-06) — `momento_del_dia(hora)` / `saludo_por_hora(hora)`, la hora local del panel en un solo lugar. Salió de `views/home_view.py` (donde era `_saludo_por_hora`) al necesitarla también el saludo del agente; los cortes 12/19 viven aquí y en ningún otro lado. Sin dependencias: no importa flet, ni Supabase, ni nada del proyecto.
  - `mesa_dao.py` (Phase 5.1) — `MesaDAO`, same shape as `PlatilloDAO` shrunk to match `public.mesas`'s two real columns (`nombre`, `orden`): `obtener_todos()`, `crear()`/`actualizar()`/`eliminar()` with the identical `EscrituraSinEfecto` RLS-silent-failure guard. `eliminar()` only removes the catalog row — it never touches `ventas`, since `ventas.mesa` is a text snapshot, not a foreign key (see the schema paragraph above).
  - `venta_dao.py` (Phase 6) — `VentaDAO`, read-only access to `public.ventas`/`public.venta_items` for the AI agent (see the dedicated Phase 6 section above): `obtener_ventas()`, `obtener_items_de_ventas(ids)`, and `obtener_ventas_con_items()` (the two combined, each venta getting its own `items` list). No write methods here on purpose — a sale is only ever opened/closed from `mesas.js`, never from the panel.
  - `ia_controller.py` (Phase 6) — `IAController`, the AI agent's brain: reads `platillos`/`mesas`/`ventas`/`venta_items` via the DAOs above, flattens them into a system prompt, and calls OpenAI (`gpt-4o-mini` by default since 2026-09-05, `gpt-4o` before that — see the dedicated Phase 6 section above for why OpenAI and not Claude/`anthropic`, and why the cheaper model is safe here). `preguntar(pregunta, historial=None)` is blocking, same convention as every other DAO — `agenteIA_view.py` is the only caller and always goes through `asyncio.to_thread`.
- `assets/` — images referenced by views/sidebar (e.g. `logomonky.png`) via relative `assets/...` paths, since `assets_dir="."` in `main.py`. `assets/logo-pensando.webp` (2026-09-06) es el logo animado que `views/agenteIA_view.py` muestra mientras la IA piensa — un WebP animado que el cliente reproduce solo, ver la Fase 6. `assets/svg/` son los cuadros sueltos de los que sale ese archivo: son la **fuente**, la app no los lee en caliente. `flet_logo.py`, en la raíz, es código de fuera que **ya no importa nadie** (se queda como referencia; ver la Fase 6 antes de volver a usarlo). `herramientas/generar_logo_pensando.py` es lo que rehace el WebP a partir de esos SVG.
- `cloudflare/index.js` (Phase 3) — source of the deployed `taku-monky-uploads` Worker (see `models/cloudflare_storage.py` above). Reference/redeploy-only: nothing in the Python app imports it, it runs on Cloudflare's edge, not in this process.
- `index.html`, `menu-platillos.html`, `menu-bebidas.html`, `menu-postres.html`, `style.css`, `catalogo.css`, `catalogo.js`, `menu.js`, `carrusel.js` (Phase 4) — the public menu site, entirely separate from everything above: no Python code runs it, no `main.py`/`MainController` involvement, nothing here imports from `models/`/`views/`. See the dedicated Phase 4 section under Design rules above for how it's structured and why the cache works the way it does. Which file each page loads: index → `style.css` + `catalogo.js` + `carrusel.js`; the 3 category pages → `style.css` + `catalogo.css` + `catalogo.js` + `menu.js` (in that order — the CSS and JS pairs each depend on the earlier file).
- `mesas.html`, `mesas.css`, `mesas.js` (Phase 5) — the internal staff sales tool, loading only each other (not `style.css`/`catalogo.js`/anything from Phase 4). See the dedicated Phase 5 section under Design rules above.
- `licencia_admin.py` — **borrado el 2026-09-05, no lo vuelvas a crear.** Era la ventana de Flet suelta (su propio `ft.run()`, su propio login, paleta gris neutra) con la que el desarrollador prendía y apagaba `configuracion_negocio.activo` de este único proyecto. `panel_licencias/` lo reemplaza y lo hace mejor (N clientes a la vez), y de todos modos había dejado de funcionar: prefillaba el correo del dueño, que desde el mismo día ya solo puede *leer* esa tabla. Su DAO, `models/configuracion_negocio_dao.py`, **sí se conservó** — ver su entrada arriba.

- `panel_licencias/` (2026-09-05) — **the developer's own licence panel, not the owner's anything.** A separate Flet app (`python panel_licencias/main.py`, its own `ft.run()`) that logs into the Supabase project of *every* client at once and lists them in one table — NEGOCIO · INICIO · FIN · RESTAN · ESTADO · pencil — so subscription dates can be set and `activo` flipped when a semester's payment lapses. It replaced `licencia_admin.py`, which was deleted on 2026-09-05 once this panel was verified working. Deliberately: **no login screen** (it runs only on the developer's machine, risk accepted), **not in `Sidebar`/`MainController`** (it is not a panel screen and the business owner must never reach it), no service_role, and no client onboarding — creating a new client's Supabase project and running its schema is separate manual work, this panel only *reads* clients that already exist. **It is 100% self-contained and must stay that way**: it imports nothing from `models/`, `views/` or `controllers/` (verified by grep) because the folder is meant to be lifted out of this repo into its own; its only dependencies are the `flet`/`supabase`/`httpx` already in `requirements.txt`. **Client credentials live outside the repo** at `%LOCALAPPDATA%\PanelLicencias\clientes.json` (same idea as `sesion.json` and `huerfanos_r2.json`) — a list of `{nombre, url, anon_key, correo, password}` objects hand-edited by the developer, read-only to the panel; `clientes.json` is in `.gitignore` anyway in case a copy ever lands inside the folder. Four files: `clientes.py` (reads/validates that file — a missing file or broken JSON renders a readable on-screen message with the path and an example, and a single malformed *row* becomes an amber warning while the good rows still load), `conexion.py` (one `supabase.Client` + login **per project** — sessions don't collide across Client instances — plus error translation for a paused free project, no internet, wrong password), `licencia_dao.py` (`models/configuracion_negocio_dao.py` made instantiable: it takes *its* client in `__init__` instead of the shared singleton, and keeps the `EscrituraSinEfecto` check, which matters more here than anywhere — it is what stops a client the panel can't actually write to from rendering as a cheerful green switch), and `main.py` (the table, laid out like `views/menu_view.py` with header and rows sharing the same column weights, but in the same neutral gray/black "zinc" palette as `mesas.css`, since this is the developer's product rather than a client's brand). **Every row loads and fails on its own**: logins run in parallel (`asyncio.gather` over `asyncio.to_thread` — serial would crawl at 10 clients) and each row catches its own errors, same rule as `home_view.py`'s cards. `RESTAN` is computed on the fly from `fecha_fin` ("faltan 12 días" / "vence hoy" / "vencido hace 3 días" / "—", amber at ≤15 days); nothing in the database computes it, because the dates stay reference-only and **the licence still never expires by itself** — that text is precisely the reminder to go flip the switch by hand. Two real Flet 0.82 traps were found by *running* it, not reading it, and are worth knowing before editing: a helper that passed `size=` both as a named default and again through `**extra` (`got multiple values for keyword argument 'size'`), and — more subtle — **`if control.page:` is not a valid mounted-check, because reading `.page` on an unmounted control raises `RuntimeError` rather than returning `None`**; the code uses a `_montada` flag plus an `_actualizar()` helper that swallows that error instead.

**Adding a new screen** means: create `views/new_view.py` following the pattern above, import it in `main_controller.py`, add an `elif` branch in `cambiar_vista`, and add a nav button in `sidebar.py` via `self._crear_boton_menu(...)`.

**Exception — the login screen** (`views/sesion_view.py`, built in Phase 2.0): it is a *startup* screen, not a section of the panel, so it does **not** go through `cambiar_vista` and gets no sidebar button. `MainController.__init__` **unconditionally** calls `mostrar_login()` (page holds only `SesionView`, full window, no `Sidebar`); `mostrar_panel()` (which builds `Sidebar` + content `Row` — that assembly lives inside `mostrar_panel()` itself, not `__init__`) is reachable only from a successful login. **This reversed on 2026-09-05 and this file used to say the opposite** ("the app skips straight to the panel on relaunch as long as the saved session is still valid — that's intentional"); it now takes an explicit product decision to bring persistence *back*, not to remove it. `cerrar_sesion()` (signs out + calls `mostrar_login()`) exists on the router already but has no caller yet — it's meant to be wired to a button in `ajustes_view.py` (Fase 8).

**Why the login is never remembered** — this is a *business* decision, not a security one, and it's the reason the whole licence apparatus exists. The developer's position: this is his software, white-labelled and personalized per restaurant, rented semi-annually. When a rental lapses, the intended effect is that the client simply can't log in any more — no panel, no `mesas.html` — and all they're left with is the public menu site, which on its own does nothing for them. **A remembered session defeats that entirely**: with a stored refresh token, an already-logged-in machine keeps working long after the cutoff, because nothing ever asks Supabase Auth again. With no persistence, every single app start performs a real `signInWithPassword` — and that call is the choke point the developer controls (either by disabling the client's Auth user, or by the `activo` lock refusing to proceed — **that lock is built as of 2026-09-05**, see the `configuracion_negocio` paragraph near the top). `mesas.js` got the same treatment for the same reason on the same day (`persistSession: false`). **A trap when verifying any of this on this machine:** Python here is the Microsoft Store build, which *virtualizes* `%LOCALAPPDATA%`, so `%LOCALAPPDATA%\TakuMonky\sesion.json` written by Python actually lands under `%LOCALAPPDATA%\Packages\PythonSoftwareFoundation.Python.3.13_qbz5n2kfra8p0\LocalCache\Local\TakuMonky\`. PowerShell and Explorer look at the unvirtualized path and report the folder as missing while the file is very much there — check it *from Python* (or resolve the path) or you'll conclude the opposite of the truth. `cambiar_vista` itself stays unchanged.

**Styling convention**: colors are hardcoded hex strings inline on controls (no theme/constants file) — the recurring palette is cream background `#fbf5e9`, near-black sidebar `#0d0905`, and gold/accent `#f4ca83`. `font_family="Georgia"` with `italic=True` is used for display headings. Match this convention rather than introducing `ft.Theme` or a separate style module unless asked.

**Language**: UI copy, comments, and variable/method names throughout the codebase are in Spanish (e.g. `cambiar_vista`, `vista_actual`, `_crear_boton_menu`). Follow this convention for consistency when adding code.
